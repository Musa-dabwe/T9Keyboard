T9 Keyboard — 5×4 Redesign Review

Analysis of the shipped screenshot + six interactive HTML mockups covering every keyboard panel. Self-contained, no external requests — open any page directly in a browser.

What the screenshot shows

Reviewed against KeyboardLayout.kt, SuggestionBar.kt, and EmojiPickerView.kt.

Bug — our own regression

QR and SPACE both claim digit "0"

QR's corner hint is 0 (it's the real numeric-page digit for that key) and SPACE's corner hint is also 0 (a leftover long-press default from the old 3×4 layout). Both are visible at once in the screenshot. KeyboardLayout.kt: KeyDef("QR", "0", …, numLabel="0") and KeyDef("SPACE", "0", …, numLabel="0", longPressChar='0') — literally the same digit assigned twice.

Accessibility

White-on-accent fails contrast for light accents

Backspace and active SHIFT hard-code white content. With the shipped accent (amber/gold, ~#FFC107-family) white-on-accent measures roughly 1.6:1 — far under WCAG's 4.5:1 minimum. Only the default blue (#558DFF) clears it comfortably.

Visual hierarchy

Enter's 🙂 hint outweighs digit hints

Emoji glyphs render at a fixed em-box regardless of declared font-size, so the 10sp hint on Enter reads noticeably larger/bolder than the numeric hints beside it, breaking the "hint = quiet corner label" convention.

Spec drift

Toolbar icons ignore the "muted until active" rule

DESIGN.md: toolbar icons should default to a muted tone and switch to accent only when active. SuggestionBar.setAccentColor() tints Settings and Edit unconditionally, so the whole toolbar always reads as "active."

Bug — unrelated panels

Emoji picker/search never adopted the new palette

EmojiPickerView.kt still hard-codes #111111 / #2B2B2B backgrounds and a fixed #E91E63 search underline instead of the shared keyboard_background and the user's accent color. The search keyboard also uses 10dp key corners vs. the main grid's 16dp.
