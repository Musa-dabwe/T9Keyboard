## 2. Blank Screen Root Cause Analysis
1. **Data loading** — In `AppBlacklistActivity.loadInstalledApps()` (lines 53-56), the code uses `pm.queryIntentActivities(intent, 0)` to find launcher apps. However, the app targets API 34. On Android 11+ (API 30+), package visibility is restricted. Without proper declarations, this returns an empty list or only a subset of apps.
2. **Threading** — `loadInstalledApps()` is executed directly on the **Main Thread** during `onCreate()` (line 35). While not the cause of the blank screen, it will cause UI stutters or ANRs as the list of installed apps grows.
3. **Adapter/State wiring** — The wiring seems correct: `adapter.submitList(appList.toList())` (line 69) is called after the list is populated.
4. **Empty state handling** — There is no empty-state view in `activity_app_blacklist.xml`. If the query returns nothing, the `RecyclerView` simply remains empty and the screen looks "broken."
5. **Lifecycle timing** — `loadInstalledApps()` is called in `onCreate()`. This is acceptable for a simple activity, but if data was loaded asynchronously, a more robust lifecycle point would be needed.
6. **Filtering logic** — The only filter is `packageName != this.packageName` (line 61), which is correct (prevents the keyboard from blacklisting itself).

### Verdict
The **Primary Root Cause** is missing package visibility declarations in `AndroidManifest.xml`. Since the app targets API 34, it cannot "see" other installed apps via `PackageManager` without either the `QUERY_ALL_PACKAGES` permission or a `<queries>` block.

## 3. learnWord() Blacklist Gate Audit
1. **Package identification** — The IME correctly uses `currentPackageName`, which is updated in `onStartInput` (line 120) and `onStartInputView` (line 127) using `EditorInfo.packageName`.
2. **Location of check** — The check is performed in `T9InputMethodService.kt` inside `onSuggestionClick()` (line 353) and `finalizeCurrentComposing()` (line 713). It gates the calls to `LearnedDictionary.learnWord()` and `LearnedDictionary.learnWordStrong()`.
3. **Cache freshness** — The blacklist is read directly from `preferences.isAppBlacklisted(currentPackage)` on every commit. Since `PreferencesManager` uses `SafeBox` (which wraps SharedPreferences), it effectively reads from memory/disk each time. This is safe but slightly less performant than a local boolean cache.
4. **Race conditions** — `currentPackageName` is set before `shouldLearn` is evaluated. No significant race condition was found.
5. **Silent skip** — The skip is silent. No logs or feedback are generated when a word is skipped due to the blacklist.

### Verdict
**Works correctly.** The integration in `T9InputMethodService` ensures that no learning occurs if the current package is in the blacklist.

## 4. Blacklist Persistence Audit
1. **Storage mechanism** — Uses `SafeBox` (v1.3.0), an encrypted SharedPreferences wrapper.
2. **Schema** — Stored as a `Set<String>` under the key `"blacklisted_apps"` (defined in `PreferencesManager.KEY_BLACKLISTED_APPS`).
3. **Consistency** — Both the settings UI and the IME service share the `PreferencesManager` class, ensuring consistent access to the same key and storage file.
4. **Initialization** — `SafeBox` is initialized in the `PreferencesManager` constructor. There is a migration block from plain SharedPreferences to `SafeBox` which is a nice touch for security.

## 7. Summary for Claude
The App Blacklist feature is logically sound and correctly integrated into the IME commit path, ensuring that private data is not learned in sensitive apps. However, the UI is completely broken on modern Android versions (API 30+) because the manifest lacks the required `QUERY_ALL_PACKAGES` permission or a `<queries>` element. Additionally, loading the app list on the main thread is a performance bottleneck. The most critical fix is adding the manifest declarations, followed by moving the package query to a background thread using Coroutines.
